# Cindy Sridharan 的三大实操案例精讲

原文出处：[How to effectively debug when you no longer understand the code](https://copyconstruct.medium.com/how-to-effectively-debug-when-you-no-longer-understand-the-code-bd3dcb2c5f7b)（2026-10-10）。
本文以工程师视角提炼作者亲身经历的三个真实案例，重点还原“为什么 AI 瞎猜”、“如何通过对照组破局”与“怎样用铁证排除假说”。

---

## 案例一：尾延迟暴涨（The Latency Bug）

### 故事经过与排查链条
1. **背景**：AI 辅助编写了一个底层存储特性，改动涉及 2 个仓库、约 9,000 行代码，拆分成 10 个按风险排序的 PR，经过了作者逐行审阅、独立 Agent 评审以及同事人工评审。预发布环境测试全部绿灯通过。
2. **故障显现**：在向大约 5,000 台客户端灰度开启该特性后约 10 分钟，客户端与服务端的 P99 尾延迟同时出现严重回退。
3. **AI 的荒谬猜想（伪根因）**：Claude 给出了一套看似无懈可击的解释：“新代码在每次 RPC 调用时都重复从磁盘重新加载 TLS 证书导致开销过大”。另一个独立的子 Agent 在评审时也直接采纳并赞同了这一解释（典型的 Agent 回音室效应）。
4. **对照组与探针破局**：
   - 寻找对照组：拿未开启特性的客户端和开启特性的客户端抓包对比 TCP 握手耗时，发现毫无差异；
   - 查验运行时：深入排查发现 TLS 证书仅在会话建立时加载了一次，根本没有每次 RPC 都重载。AI 的假设被运行时证据一票否决！
5. **强信号突破**：对比两组的 DNS 解析记录，发现了巨大差异：**未开启特性的对照组 DNS 仅返回 5 个 IP 地址，而故障组居然解析出了约 400 个 IP 地址！**
6. **最终真实机制**：AI 编写新 mTLS 路径时，用错了客户端类——本该使用带分片路由的 `ShardedDatabaseClient`，却误用了普通 `DatabaseClient`。这导致客户端将请求随机打到了 400 个 Pod 中的任意一个，被打中的 Pod 自身没有对应数据，必须再跨 Pod 转发去正确的分片拉取，从而拖垮了整条链路的尾延迟。
7. **修复与启示**：修复代码其实只有 1 行（换回正确的客户端类）。为什么单测和预发没拦住？因为预发环境只有 2 个分片、每片 1 个副本，随便打都能打中，规模掩盖了问题；而生产环境有 5 个分片、每片 80 个副本，跨 Pod 转发的几率大幅飙升。

## 案例二：无凭证引发 50GB 内存打爆（The Memory Leak）

### 故事经过与排查链条
1. **背景**：系统在未提供有效凭证（如 Token 失效或未配置）时，Docker 容器直接被内核 OOM-killer 强制杀死。用户提供了好坏版本、稳定的复现步骤，以及一份 heaptrack 堆分析报告（显示在 OOM 前堆内存分配高达 50 GB）。
2. **AI 的离谱排查方向**：
   - Claude 咬定是“Token 验证被拒后引发了 13.7 万次重试，导致内存中积攒了海量的 JSON 日志”——但作者对业务逻辑很清楚，该状态在线上根本不可能发生，纯属瞎猜；
   - Claude 接着又归咎于近期的“API 摊销优化与遥测”变更，但作者一查配置，该优化特性默认是关闭的（Opt-in 且未开）；
   - Claude 提出对过去 24 个提交进行逐一二分排查（Bisect），被作者果断拒绝，要求沿真实的堆栈调用向下追踪。
3. **关键事实与两重机制组合**：
   - 查看 heaptrack 真实调用堆栈，发现执行的是普通的递归方法 `runStateMachine`，而不是优化版入口 `dedupedRunStateMachine`；
   - 梳理发布变更发现：虽然 API 摊销优化没开，但**随同发布的一个进程级缓存却是默认开启的**！
   - 原先的认证引擎是“单次使用（Single-use）、会话结束即销毁”的；新缓存将其生命周期延长至与进程同生共死。当用户无凭证发起请求时，耗尽的状态机被不断重入；而 Swift 的异步递归没有尾调用优化，递归栈帧被死死留在内存中无法释放。
4. **启示**：这是一个典型的“双因组合”故障——单一原因都无法完整解释：新缓存解释了为什么近期才暴雷，单次状态机的重入递归解释了为什么内存沿此路径暴涨。不能胡乱拼凑原因，但也不能在面对复杂复合机制时盲目单因归罪。

## 案例三：神秘 60 秒卡死与内核断案（The Hang）

### 故事经过与排查链条
1. **背景**：桌面守护进程通过虚拟文件系统（VFS）向用户提供远端文件访问。用户间歇性遭遇 VFS 请求卡死 60 秒后超时，无任何崩溃日志，重启程序又会瞬间抹掉现场，偶发极难复现。
2. **排查受阻与甩锅**：
   - 服务端日志完全正常；
   - 抓包显示客户端与远端的 TCP 握手和 WebSocket 升级均已成功，之后只剩下无意义的 ping/pong 心跳报文，业务读写完全未开始；
   - 业务逻辑显示：桌面端必须先向本机的认证守护进程（通过 Mach/XPC 本地进程间通信）拿到 Token，才会去远端发起读写；
   - 认证模块团队最初用“我们这边一条报错日志都没有，说明你们压根没给我们发过请求”为由拒绝排查。
3. **逐层探针下潜与内核铁证**：
   - 日志无果 → 抓包无果 → 分析系统诊断包（sysdiagnose）中的 `lsmp`（列出 Mach 端口状态）；
   - 在一份 30 MB 的 `lsmp` 端口转储文件中找到关键铁证：**认证进程在收到请求 67 个小时之后，居然仍死死持有该 XPC 请求的一次性回复权（Reply Right）未作应答！**
   - 随后在多个其他用户的诊断包中均确认了相同的内核端口挂起模式。事实胜于雄辩：请求确实送到了，但认证进程漏掉了 completion handler 回调，导致客户端死等。
4. **识破“假复现”陷阱**：
   - 排查期间，一位同事声称成功“复现”了 60 秒超时——他通过手动篡改系统时间模拟时钟偏差，也诱发了超时。
   - 但用抓包与内核信号一比对，发现同事的场景是远端由于时间不对拒绝了 Token，客户端正在不断重试建连，内核中根本不存在挂起的 IPC 回复权。这完全是另一个独立的 Bug，绝不能当作原故障去修！
5. **启示**：表现为同样的超时，不代表是同一个故障；当应用层日志失真或缺失时，向底层网络与内核探针下潜，能拿出令跨团队无可辩驳的交接铁证。
