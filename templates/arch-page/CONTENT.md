# 内容约束：一篇架构分析页要生成什么

模版负责渲染，这份文件规定内容。每一项都写成“必须有什么、写到什么程度、从哪里取证”。引擎和 `check_page.cjs` 会校验第 2–4 节的引用关系；其余规则靠作者按第 6 节清单自查。

## 1. 页面结构

页面固定为三部分，按下表顺序排列：

| 部分 | 回答的问题 | 内容来源 |
|---|---|---|
| 总体架构 | 系统由哪几块组成，主路径怎么走 | Archify 架构图 + `overview.nodes` |
| 详细架构流程 | 一次真实运行里，数据在组件之间怎么流动 | 组件卡片、连线、真实录制的流程 |
| 对象架构 | 每块组件里有哪些对象，各自持有什么、提供什么 | `components` |

三部分之外的章节（样例文件、代码索引等）通过 `toc`、`sections`、`page.js` 追加在后面。

页首文档信息（`page.config.json` 的 `text`）全部填写：

| 键 | 页面上的名称 | 写法 |
|---|---|---|
| `DOC_SCOPE` | 代码范围 | 仓库地址 + 40 位提交号；分析限定的目录 |
| `DOC_REQUIREMENT` | 关联需求 | 需求单或问题链接；个人研究写研究目的 |
| `DOC_GOAL` | 目的 | 读完能回答的问题，一到两句 |
| `DOC_READERS` | 读者 | 具体角色及其已有背景 |
| `DOC_SHOWS` | 呈现 | 本页覆盖的组件、流程、对象 |
| `DOC_EXCLUDES` | 不呈现 | 明确划出范围的内容，并写出它们在哪里可以找到 |
| `DOC_BUILD` | 生成方式 | 构建命令、录制命令、数据日期 |

## 2. 总体架构

- **组件数 8–12 个。** 每个组件对应一个能在源码里指出目录或包的单元。少于 8 个时拆开职责最重的组件；多于 12 个时合并同层且总是一起出现的组件。
- **主路径。** 用一条连续的实线从入口走到持久化或外部服务，旁路用虚线。
- **分层。** 按运行位置分组（进程外客户端、协议层、核心循环、插件、存储、外部服务），每组一种颜色。
- **证据。** 每个组件的 `sources` 列出 1–3 个文件，文件必须存在于 `meta.repository.revision` 指向的提交。
- **点击说明。** `overview.nodes` 为每个组件提供：
  - `kicker`：所在层；
  - `title`：组件名；
  - `text`：两到四句，写它接收什么、产出什么、状态存在哪里；
  - `src`：带行号的源码引用；
  - `pano`：跳到详细架构流程中最能体现它的一步。
- **导读（`overview.intro`）。** 页面打开时显示在说明栏，点任一方框后换成该方框的说明。写法：用一行箭头串出主路径，再用一到两句交代支线和后台写入。
- **说明条（`overview.notes`）。** 2–4 条，每条写一个横跨多个方框的规则，例如循环条件、审批顺序、流式回传；需要展开时用 `[文字](#锚点)` 链到额外章节。

## 3. 详细架构流程

### 3.1 组件卡片（`pano.nodes`）

- **数量 9–15 张。** 可以比总体架构更细，例如把“会话”拆成“会话日志”和“持久化”。
- **每张卡片的字段：**

  | 字段 | 写法 |
  |---|---|
  | `name` | 中文名 |
  | `code` | 代码里的类名、包名或文件名 |
  | `job` | 一到两句，写它做什么 |
  | `fact` | 一句“要点”，写读者最容易误解的事实，例如执行顺序、谁持有锁、数据存在内存还是磁盘 |
  | `terms` | 1–3 个关键概念 id |

- **布局。** `at: [行, 起始列, 跨列]` 按数据流从上到下排列，同层组件放在同一行。图例占一个格子。

### 3.2 关键概念（`pano.terms`）

- **每个概念写成 `[名称, 定义]`。** 定义一到两句，写它在这个系统里的具体含义和出现位置，例如“写盘水位：已落盘的最大 seq，恢复时从它之后补写”。
- **每个概念至少被一张卡片引用。** 引擎把零引用的概念、指向登记表以外 id 的引用写成控制台错误。
- **只收录读懂流程必需的词。** 通用名词（HTTP、JSON）只在系统给了特殊用法时收录。

### 3.3 连线（`pano.edges`）

- `label`：写线上传的数据，例如“JSON-RPC 请求”“事件帧”，避免“调用”“交互”这类动词。
- `how`：写传输方式和触发条件，例如“同进程函数调用，每帧一次”。
- `dash: true`：用于旁路、异步写、观察者通知。
- `route: 'left'|'right'`：连线需要跨过中间几行卡片时，从画布侧边绕行；同侧多条用 `lane` 错开。
- `empty`：经过这根线的小步数为 0 时显示，写它在什么场景下出现。
- 每根线的两端都是已登记的卡片。

### 3.4 流程（`pano.stories`）

- **3–5 个流程，全部来自真实运行的录制。**
  - 第一个是最常见的主路径，例如一轮对话；
  - 其余各覆盖一种关键分支：失败重试、崩溃恢复、分叉或子任务、并发冲突。
- **`intro`。** 写这个流程是怎么录的：命令、输入、注入的故障。

### 3.5 大步（`steps`）

- **一个大步是读者能用一句话命名的阶段**，例如“启动”“组装请求”“流式返回”“写盘”。遇到以下情况就切出新的大步：
  - 控制权换到另一个组件；
  - 等待外部响应；
  - 阶段性结果落地。
- **每个大步的字段：**
  - `t`：标题；
  - `text`：两到三句，写这一阶段的输入、产出和关键判断；
  - `src`：1–3 处源码引用。
- **小步数量建议 3–30 条。** 超过 30 条时按子阶段拆成多个大步。
- **规则步。** 讲整体规则（判定顺序、配置项、触发时机）的大步小步数为 0，用 `extra` 放附表，用 `data` 放代表性数据。规则步在一个流程里占少数，其余大步都由录制的小步组成。

### 3.6 小步（`subs`）

- **一个小步对应录制里的一条记录。** 记录来源包括：
  - 一次跨边界的消息（协议行、HTTP 请求或响应、写盘）；
  - 一次进程内事件分发。
- **每个小步的字段：**

  | 字段 | 写法 |
  |---|---|
  | `t` | 记录本身的标识，例如 `seq 4 turn/start`、`POST /v1/messages #1`、`← result #req_2` |
  | `n` | 经过的卡片，按顺序；只有一个时表示发生在该组件内部 |
  | `e` | 经过的连线 `from>to` |
  | `text` | 先写相对时间 `t = 1.587 s`，再用一到两句写这条记录造成的结果 |
  | `data` | 1–3 个数据框，内容是录制原文 |

- **说明文字写结果，数据框放证据。** 字段含义交给 `fieldDoc`，`text` 里只写读者需要的结论。

### 3.7 数据登记

数据框按登记信息自动拆层、逐字段说明：

| 配置 | 内容 |
|---|---|
| `media` | 传输媒介，例如协议消息、进程内对象、网络请求、文件 |
| `kinds` | 每种数据类型属于哪种媒介，以及“谁 → 谁 · 什么” |
| `peel` | 外层信封逐层剥开的规则，返回内层字段名和这一层的名称；页面把外层字段折叠，主体字段直接展示 |
| `fieldDoc` | 字段名到含义的表 |
| `dataTag` | 数据来源标签，例如“录制” |

- 每个数据框都标注 `k`（数据类型），类型必须在 `kinds` 中登记。
- 逐行文件用 `{ t: 'jsonl', v: [...], line: '<逐行数据类型>' }`。
- 敏感字段（密钥、令牌、Cookie）在录制阶段替换为 `[redacted]`。

### 3.8 数据采集

流程数据来自一次真实运行。录制工具在系统的每条边界上旁路记录，被分析代码保持原样：

| 边界 | 采集方式 | 记录内容 |
|---|---|---|
| 进程间协议 | 驱动脚本作为客户端启动被测进程，逐行读写 stdio 或 socket | 方向、方法、id、完整消息 |
| 进程内事件 | 用预加载模块包裹事件总线的分发函数，进入和退出各追加一行 JSONL | 事件名、参数快照、返回值、耗时、监听者数 |
| 外部服务 | 把服务地址指向本地录制代理，代理转发上游并记录 | 请求头（脱敏）、请求体、状态码、流式分片 |
| 文件 | 轮询数据目录，比较大小，读出新增部分（必要时解压） | 路径、前后大小、新增行 |

- **录制格式。** 每条记录带统一时间轴 `t`（相对启动毫秒）、`lane`（边界）、`kind`、`label`、`data`。
- **归约脚本。** 再把原始记录转成页面数据：
  - `events`：保留的原始记录；
  - `rows`：每行带 `from`、`to`、`kind`，直接对应一个小步。
- **分支场景通过录制工具注入。**
  - 失败重试：代理对指定请求返回一次错误；
  - 崩溃恢复：在指定事件后杀进程，再用恢复命令重启；
  - 分叉：驱动脚本发起分叉请求。
- **参数快照有上限。** 字符串、数组和递归深度都要限制。循环引用、函数、大对象写成占位文字，例如 `[Circular]`、`[Function name]`、`[Session]`。

## 4. 对象架构（`components`）

- **对象数量。** 每个总体架构组件对应 1–3 个对象，`graph` 填该组件的 Archify id；校验逐个核对每个 Archify 组件都有对象。
- **每个对象的字段：**

  | 字段 | 写法 |
  |---|---|
  | `object` | 代码里的类型名，多个用 ` · ` 分隔 |
  | `plain` | 两到三句，写它负责什么 |
  | `state` | 它持有的关键属性，`[属性, 说明]` |
  | `methods` | 3–6 个对外方法：`sig` 写成 `Type.method(a, b) -> Ret`，`in`、`out`、`effect` 各写一句 |
  | `rel` | 与其他对象的关系，`[使用/通知/创建/持有, 对象 id, 说明]` |
  | `boundary` | 它的职责边界：哪些事由它完成，相邻的事交给谁 |
  | `src` | 定义所在的源码行 |

- **名词条（`componentNotes`）。** 3–6 个贯穿全页的核心名词，每个一句解释，放在对象图下方，例如“会话”“回合”“条目”。

## 5. 写作规则

- **全文中文。** 代码标识符、字段名、命令保持原文，用反引号包裹。
- **只写确定的现状。** 写它做什么、在哪里、由谁完成、结果是什么。否定句只用于代码里可验证的契约（例如校验失败时拒绝），并在同一句写出实际发生的事。
- **源码引用。** 一律写成 `path:起-止`，路径相对仓库根，`repo` 前缀固定到 40 位提交号。
- **数字取自录制。** 时间、字节数、条数都从录制数据计算，与数据框里的原文一致。

## 6. 完成清单

1. `python3 build_page.py` 构建成功，所有占位符都已填写。
2. 运行 `python3 check_src.py <被分析仓库> arch.data.js`，结果为 0 broken。
3. `check_page.cjs` 返回 0。这一步覆盖以下几项：
   - 总体架构的每个方框都有说明；
   - 每个对象都能打开；
   - 每个大步都能用“下一步”到达；
   - 每个小步展开后都有数据框，同一时间只展开一条；
   - 连线跳转能展开对应的小步。
4. 对页面文字和文档做一遍不字检查（第 5 节第二条）。
5. 截图核对：
   - 总体架构；
   - 一个大步展开第一条小步；
   - 一个多层信封的数据框。
