## dsh 是什么，和 Codex、oh-my-pi 有什么不同

- **同一个 loop 骨架**：采样 → 收集工具调用 → 执行 → 有工具结果或新输入就继续。
- **不同的是策略放在哪**：Codex 写在 loop 内部，oh-my-pi 放在 loop 上层，dsh 放进插件。dsh 的 loop 只有四个扩展点（step 前、请求配置、请求出错、turn 即将结束），重试、压缩、续跑、拒绝全部由插件实现；连 loop 本身也是一个插件。
- **两个独特的核心**：
  1. **会话日志是唯一真源**：连排队的输入都是日志投影，每次请求都从日志推导，并在发出前校验。
  2. **组合内核**：整个产品是一棵可热重载的插件树，每个注册都绑定清理动作，禁用即撤销。

如果读过本博客的 [Codex / oh-my-pi 系列](/personal-blog/articles/codex-omp-guide/)，dsh 可以当作第三个样本来读：前两者建立的概念（turn、step、配对不变量、读写锁式并行、只追加上下文）在这里都有对应，只关注增量即可。没读过也没关系，本系列是自足的。

## 推荐顺序

### 第一步：架构设计第一部分的前四节，建立全局

读"定位与设计目标""概念模型""组件视图""组合内核"四节，配合组件总览图和组合装配图。

这一步要掌握：

1. 五条设计目标：一切可撤销、日志是真源、loop 极简、前缀缓存与服务端协同、fail-closed。
2. 概念表里的几个 dsh 特有概念：行、effect、surface、投影、收件箱、作用域、预设。
3. Profile → Bundle → Patch 的叠加顺序，以及"覆盖是整字段替换"。
4. 所有协议驱动都是"agent 工厂的适配器"。

### 第二步：D1 Agent Loop，看主循环

读第 5 节，配合 turn 状态机图和 step 时序图。这是整个系列的核心。

这一步要掌握：

1. 七层分层，以及"持久状态只有日志"。
2. `followup / steer / inject` 三种输入与两级收件箱；插话在下一个 step 边界才生效。
3. turn / step 状态机的 10 个状态和全部停止条件；没有步数上限。
4. 四个扩展点各自决定什么；"turn 即将结束"只能通过插话续跑。
5. 配对不变量的多层防线，以及崩溃恢复"不重跑、只补齐"。

### 第三步：D3 工具与 D5 安全，看副作用如何被约束

读第 6、7 节，配合工具执行管线图。

相对第二步的增量：

1. 统一管线的十来个阶段，以及两个反直觉的顺序：参数校验在工具体内部、执行前钩子不能改写参数。
2. 工具在流结束后调度；只有工具体并行，审批和策略按模型顺序串行。
3. 审批只针对"提权"，只有"允许一次"；沙箱只管文件写，被拒后不自动升级。
4. 计划模式不是安全机制。

### 第四步：D4 上下文与 D2 LLM，看缓存与服务端协同

读第 8、9 节。

1. 系统提示词作为第 0 号节点、变化时追加；工具增删用开发者消息表达。这两点依赖 DeepSeek 服务端的扩展语义。
2. 压缩的三个触发点和"先裁剪后摘要"。
3. 重试为什么在插件里，以及重试本身也写进日志。
4. **数据外发**：默认配置下完整会话日志会随请求同步给 DeepSeek，以及怎样关闭。

### 第五步：D6 编排、D7 扩展与其余章节

读第 10 ～ 16 节：子 agent 的继承与隔离、各种编排机制如何不改主循环、扩展的发现与撤销、持久化语义、不变量与巧妙之处汇总、已知局限、0.1.7 → 0.2.0 的变化。

### 第六步：自带文档总结，补上外部契约

读自带文档总结。官方文档很全（572 个文件），适合当查阅入口；重点看"文档与源码不一致"一节，避免被过时描述误导。

### 第七步：与 Codex、oh-my-pi 对比，收束

读对比篇。它把三者放进同一组对照表，最后给出一份"自己实现 agent loop"的清单，比 Codex / oh-my-pi 那份多了三条来自 dsh 的做法。

### 延伸：资料索引

收录了近两个月的 dsh 解析文章、书、视频和改写项目，并标了每份资料的版本基线和可信度。想逐函数读执行循环，可以配合其中推荐的几份。
