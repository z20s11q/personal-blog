> 这组文章基于两个开源 coding agent 的源码快照：openai/codex `44fe510c`、can1357/oh-my-pi `df731d51`（均为 2026-09-28）。本篇说明先读什么、后读什么，以及每一步在前一步的基础上多学到什么。

## 两个项目的关系

- **同一个 loop 骨架**：采样 → 收集工具调用 → 执行 → 只要有工具结果或新的用户输入就继续。
- **难点不同**：Codex 的难点在安全和协议（审批、隔离执行、被拒后升级重试、自动审查、会话协议状态机）；oh-my-pi 的难点在模型兼容和交互体验（适配几十家 provider 和各种不守规矩的模型，让插话尽可能即时又不丢消息）。
- **同构的解法**：读写锁语义的工具并行、为每条中断路径合成配对的工具结果、只追加的上下文、压缩作为 loop 内的一等事件。

所以路线是：先用一个项目把骨架和通用机制学扎实，再看同一骨架如何被另一个项目推向不同方向，最后横向对比，提炼出可复用的设计。

## 推荐顺序

### 第一步：Codex 架构设计，建立基线

读 [Codex 架构设计](/personal-blog/articles/codex-architecture/) 的第一部分，配合 [Codex 交互式架构图](/personal-blog/articles/codex-diagrams/)。

先读 Codex 的理由：

- **分层最显式**：Op 分发 → 任务 → Turn 循环 → 采样，四层各有独立职责。“谁决定继续、谁负责重试、谁派发工具”在这里最容易看清。
- **安全链路最完整**：策略判定 → 审批 → 隔离执行 → 被拒升级，是理解“模型产生的副作用如何被约束”的最完整样本。
- **后文以它为参照**：oh-my-pi 架构设计按同一骨架写成，并多处直接与 Codex 对照。先建立 Codex 的概念，读 oh-my-pi 时只需关注增量。

这一步要掌握：

1. 四层循环各自的职责，以及 turn 的继续条件。
2. 工具调用边流边派发、流结束后按派发顺序收割结果。
3. 并行门的读写锁语义，以及取消时如何合成结果。
4. 审批 → 选沙箱 → 执行 → 被拒升级的编排流程。
5. 上下文只追加、世界状态差异注入、turn 前 / turn 中途 / turn 后三处压缩。

图的阅读顺序：组件总览 → Turn 循环状态机 → 一次采样的时序 → 工具编排流程。

### 第二步：Codex 自带文档总结，补上外部契约

读 [Codex 自带文档总结](/personal-blog/articles/codex-bundled-docs/)。架构设计讲内部机制，官方文档讲外部契约：协议状态机（Thread / Turn / Item）、hooks 挂载点、审批模式、配置与上下文预算。读完能分清哪些行为有文档承诺，哪些只能从源码得知；该篇“文档没覆盖、必须读源码的部分”一节列了清单。

### 第三步：oh-my-pi 架构设计，看同一骨架的另一种推法

读 [oh-my-pi 架构设计](/personal-blog/articles/omp-architecture/) 的第一部分，配合 [oh-my-pi 交互式架构图](/personal-blog/articles/omp-diagrams/)。两篇的章节都按七个子系统组织，建议与 Codex 架构设计逐节对照。

相对 Codex 的增量：

1. **结构**：会话层 → Agent → Agent Loop 三层。loop 无状态，配置每次调用前重读；压缩、重试等策略放在宿主，通过 turn 结束钩子挂进来。
2. **插话**：插话 / 续话 / 旁白三种输入；可中断工具与协作式软信号；投递记账，出队不等于送达。
3. **模型兼容**：统一的流事件，文本内工具调用方言，处理模型把内部格式泄漏到文本里的情况。
4. **工具调度**：共享 / 独占可以按参数动态判断；可选的推测执行（只读工具，最多 2 个在途）与定稿后的参数对账。
5. **持久化与编辑**：只追加的会话树、Hashline 编辑、流式规则（TTSR）。

图的阅读顺序：组件总览 → 主循环状态机 → 插话时序。

### 第四步：oh-my-pi 自带文档总结，按专题查阅

读 [oh-my-pi 自带文档总结](/personal-blog/articles/omp-bundled-docs/)。oh-my-pi 自带 134 篇专题文档，这篇是它们的地图，并列出了文档与源码不一致之处。适合当作查阅入口，不必通读。

### 第五步：两者对比与可借鉴点，收束

读 [两者对比与可借鉴点](/personal-blog/articles/codex-vs-omp/)。它把前四步的内容放进同一组对照表：loop 结构、工具并行、边流边执行、插话、中断与配对、上下文与缓存、压缩、重试、安全、扩展点，最后给出“自己实现一个 coding agent loop”的优先级清单。

### 延伸：资料索引

[资料索引](/personal-blog/articles/codex-omp-research-index/) 收录了近两个月网上的相关解析、改写项目和同类架构分析框架。其中 arXiv 2609.00006 提出的七个子系统，就是两篇架构设计第一部分的章节骨架。

## 时间有限时

只读三篇：Codex 架构设计第一部分 → oh-my-pi 架构设计第一部分 → 两者对比与可借鉴点。图和两篇自带文档总结按需查阅。

## 读源码时

先在架构设计的第二部分“实现映射”里找到位置，再按该部分最后的“源码阅读路线”看代码。Codex 从 `core/src/session/turn.rs` 的 `run_turn` 开始，oh-my-pi 从 `packages/agent/src/agent-loop.ts` 的 `runLoopBody` 开始。
